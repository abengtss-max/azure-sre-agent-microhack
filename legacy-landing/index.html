Azure SRE Agent · MicroHack

Keep Aetherion AirOps flying.

Aetherion AirOps is a Tier 0 aviation operations platform — flight ops, crew scheduling, reservations, baggage and telemetry — running on Azure Kubernetes Service behind API Management. In this MicroHack you injected incidents one at a time and use the Azure SRE Agent to detect, diagnose and resolve them, grounded in real runbooks.

Get started

Everything you need before challenge 1.

1. Open the Ops Center

Your live dashboard shows service health, an operational-risk gauge, a flight map, incidents and business impact. Your facilitator shares the exact HTTPS URL (it looks like https://sreagenthack-XXXXX.<region>.cloudapp.azure.com).

2. Connect the SRE Agent

In the Azure portal, attach the aetherion-sre-agent to the resource group. Begin in Reader (read-only), then switch to Review (approval-gated) when you are ready to let it act.

3. Open Grafana

Azure Managed Grafana is wired to Azure Monitor / Application Insights for metrics, traces and logs. Use it to corroborate what the agent tells you.

4. Have the repo handy

The start-challenge / check-challenge scripts live in the repo under scripts/. Run them from a terminal with kubectl pointed at the aetherion-aks cluster.

The SRE Agent is never simulated. The scripts only inject faults and grade your fix — the detection and diagnosis are genuinely the agent's job.

Self-serve workflow

Two commands drive every challenge. Progress unlocks linearly.

start-challenge N

Injects the incident for challenge N — the root cause stays hidden. You get a customer-style alert, nothing more.

./scripts/start-challenge.ps1 1

check-challenge N

Grades your remediation against live cluster / APIM state. Passing unlocks the next challenge. Symptom-only or "wait it out" fixes will not pass.

./scripts/check-challenge.ps1 1
Do not read the fault-injection scripts while a challenge is open — that spoils the diagnosis. Let the SRE Agent find the root cause.

The challenges

One continuous storyline — work top to bottom. Challenges 2 and 3 are a single ongoing incident seen in three phases; each fault persists until you truly fix it.

1
Welcome & Operational Baseline
Connect read-only, learn the estate, then capture a healthy baseline
 Config

You are the new reliability team for a global airline platform. Connect the SRE Agent in Reader + Review, let it enumerate the estate, and confirm a write request asks for approval. Then record a full healthy readout — deployments, replica counts and typical check-in latency — so you can spot deviations later.

Objective

Agent connected read-only, all services healthy, Grafana open, baseline captured.

Run
./scripts/start-challenge.ps1 1
./scripts/check-challenge.ps1 1   # self-attest
2
Detect & Investigate the Check-In Degradation
Detect the symptom, then read-only root-cause analysis
 Fault

Online check-in slows as a passenger surge builds. Capture evidence that booking latency is abnormal versus your baseline — and change nothing. Then correlate latency with CPU and replica count to separate added, load-independent latency from genuine capacity pressure and form an evidence-backed hypothesis.

Success

Symptom documented with evidence and a defensible root-cause hypothesis; no change made.

Run
./scripts/start-challenge.ps1 2
./scripts/check-challenge.ps1 2   # self-attest
3
Controlled Recovery & the Deployment That Changed Everything
Governed remediation, then correlate a total failure with a change
 Fault

Get the agent's plan first, then apply the least-disruptive fix via on-behalf-of approval or a narrow role — clear the added latency and let autoscaling absorb load. Then the flight board goes dark: correlate the failure with rollout and repository history and apply a reversible rollback, not a rebuild.

Success

Booking healthy at baseline latency and flight-ops serving data again; every write governed.

Cost-Aware Operating Model & Autonomous Recovery
Govern the agent's consumption, then let it recover a bounded incident
 Fault

Review the agent's consumption by thread type and purpose and write a balanced operating model — cost, isolation, RBAC and ownership; balanced, not cheapest. Then the baggage service returns errors on a slice of traffic: grant a bounded autonomous posture and let the agent recover it end-to-end while you supervise. Don't fix it by hand.

Success

A defensible operating model, and baggage healthy again — remediated autonomously within guardrails.
